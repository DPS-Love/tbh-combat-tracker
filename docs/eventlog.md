# 战斗日志格式（v1）

每局游戏写一份：`BepInEx\TbhCombatTracker\logs\tbh-yyyyMMdd-HHmmss.tbhlog.gz`。
gzip 压缩的 UTF-8 文本，一行一个事件；解压后可以直接看。保留天数见配置项 `LogRetentionDays`。

**日志记录的是事件，不是统计结果。** 分段、归因、分桶都由解析器（`CombatParser`）从事件算出来，
实时统计和导入日志走的是同一个解析器。所以：

- 面板上实时看到的数字，和日后导入这份日志看到的数字逐项一致（记录端先把金额和时间规整成日志里的写法再分发）
- 解析器以后加了新维度、改进了分类规则，旧日志重新导入也能按新规则算

## 文件结构

```
#TBHLOG|1
#META|mod=0.3.0|game=1.2.8|start=2026-09-23T11:22:08.1234567+08:00
0.512|U|-51234|H|2|Hero_201|游侠
0.512|A|3|SkillName_20101|快速射击
0.512|U|-60012|M|0|Monster_30043|Monster_30043
0.512|D|-51234|-60012|8123.46|10234|1|2|1|3
…
#END|events=123456
```

- 第一行 `#TBHLOG|版本号`。读的时候没有这一行就不认作战斗日志。
- `#META` 是键值对：`mod` 插件版本、`game` 游戏版本、`start` 会话开始的本地时间（ISO 8601，带时区）。
- `#END` 是正常退出时写的结束标记。没有它说明游戏被强杀或还在写——读到哪算哪，主面板会提示"末尾不完整"。
  写日志的线程每 2 秒做一次 gzip 同步刷新，所以最多丢最后 2 秒。
- 其它以 `#` 开头的行是注释。

## 事件

每行第一个字段是**会话内秒数**（从插件加载起算，保留 3 位小数），第二个是事件字母，后面按类型解释。
空字段表示"不知道"。文本字段里的 `\`、`|`、换行分别转义成 `\\`、`\p`、`\n`。

| 字母 | 含义 | 字段 |
|---|---|---|
| `U` | 单位定义：第一次出现、或名字 / 职业变了时写一条 | `id` `种类` `职业` `稳定键` `显示名` |
| `A` | 技能定义：分配会话内编号，伤害行只写编号 | `编号` `稳定键` `显示名` |
| `D` | 对怪物造成的伤害 | `攻击者` `目标` `数值` `原始值` `暴击` `类型` `元素` `技能` |
| `T` | 英雄承受的伤害 | `英雄` `攻击者` `数值` `原始值` `暴击` `类型` `元素` `技能` |
| `H` | 英雄获得的生命恢复 | `英雄` `施法者` `数值` `判定` `标志B` `标志C` `括号` |
| `S` | 关卡信号：`name` 关卡名文本、`start` 是否开始（0/1）、`wave` 波次状态 | `子类型` `值` |
| `R` | 玩家手动重置（F10 / 浮窗上的「重置」） | — |

字段说明：

- **id**：Unity 实例 id，一局之内唯一。`0` 表示没有具体单位（环境伤害、陷阱、召唤物主人已死）。
  英雄用英雄本体的 id；怪物用它血条组件的 id。
- **种类**：`H` 英雄 / `M` 怪物 / `O` 其它（召唤物、建筑…）。
- **职业**：`EEquipClassType`，1 骑士 2 游侠 3 法师 4 牧师 5 猎人 6 杀手，0 未知。
- **稳定键**：不随语言变的名字。单位是 GameObject 名去掉 `(Clone)`（`Hero_201`、`Monster_30043`）；
  技能是 `SkillNameKey`（`SkillName_20101`），没有就用技能类名（`MonsterActive`）。
- **显示名**：记录时玩家语言下的名字，导入时直接显示。
- **数值**：实际扣掉 / 回复的生命值（保留两位小数）。
- **原始值**：伤害结算前 `DamageInfo.OriginDamage` 的原值。实测最终伤害常是它的若干倍（比如正好 4 倍），
  它不是"减免前的伤害"，含义以游戏为准，原样记下留给以后的分析。
  这一项和暴击、类型、元素一样来自伤害结算的分类上下文，没有上下文时四项全空。
- **类型**：`EDamageType` 位标志，Melee=1、Projectile=2、AOE=4、Summon=8、DOT=16、Trap=32。
- **元素**：`EDamageAttribute`，Physical=0、Fire=1、Cold=2、Lightning=3、Chaos=4、AllElement=5、None=6。
- **施法者**：技能治疗归因到的英雄；`0` 表示自愈（生命偷取、自然回复…），统计时算在被恢复的英雄自己头上。
- **判定**：记录时判定的恢复来源，0 自然回复、1 战斗回复、2 处决回复、3 治愈、4 圣域、5 技能治疗。
- **标志B / 标志C**：恢复总入口的两个 bool 参数（`0/1`），恢复没经过总入口时为空。
- **括号**：记录时所在的上游括号（同上的编号，0 = 不在括号里）。判定依据的原始事实都在日志里，
  以后改进分类规则时旧日志也能重新分类。

## 兼容规则

- **只加不改。** 已发布的字母和字段含义永远不变。新信息用新的事件字母，或者在已有行的**末尾**追加字段。
- 读的一方遇到不认识的事件字母就跳过（计入"不认识"），多出来的字段忽略，缺的字段按"不知道"处理。
  所以旧版本能读新日志（只是看不到新信息），新版本能读旧日志（新维度在旧日志里为空或按旧规则推算）。
- 行格式不兼容的改动才升版本号。解析器对更高的版本号照读不误，只是按自己认识的部分解析。

## 加一个统计维度

1. 需要的原始信息日志里已经有了（比如"对每种怪物的伤害"——`D` 行里有目标，`U` 行里有怪物的稳定键）：
   只改 `CombatParser` 和界面，旧日志导入就能看到。
2. 日志里还没有：在记录端（`DamageTracker` / `Patches`）把原始信息加进事件，按上面的兼容规则扩展格式，
   再改解析器。之后写的日志就有这项数据。

## 离线查看与测试

```powershell
dotnet run --project tools/logcheck -- <日志文件>   # 会话概要、事件密度、每段统计
dotnet run --project tools/logcheck -- --test       # 解析器的合成测试
```

`tools/logcheck` 直接编译插件里的解析器源文件（`CombatModel` / `CombatEvent` / `EventLogFormat` /
`EventLogReader` / `CombatParser`）。这几个文件不能引用 Unity、BepInEx 或游戏类型，谁引用了，那边就编译不过。
